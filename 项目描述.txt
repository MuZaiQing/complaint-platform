# 多源消费者投诉智能分析与预警平台

## 整体项目方案（结合当前已完成成果的最终落地版）

---

## 一、项目定位与建设目标

### 项目背景

面向 CFPB 金融消费者投诉、FCC 电信投诉两类多源公开数据，构建一套**分布式存储 + 大数据计算 + 可视化展示 + 智能预警**的完整分析平台，实现从原始数据到业务洞察的全链路落地。

### 核心目标

1. **展示大数据技术能力**：基于 Hadoop HDFS + Java MapReduce 完成海量数据的分布式存储与多维度聚合计算；
2. **产出业务分析价值**：从时间、产品、地区、企业、文本等多个维度挖掘投诉规律与核心痛点；
3. **形成可展示成果**：搭建可视化大屏与分析页面，直观呈现分析结论，支持交互查询与风险预警；
4. **保证技术严谨性**：所有分布式计算结果与本地计算交叉验证，数据口径清晰可追溯。

---

## 二、整体技术架构（分层设计，职责明确）

采用**五层架构**，每层技术栈单一、职责清晰，无重复建设。

| 层级 | 技术选型 | 核心职责 |
| --- | --- | --- |
| **展示层** | Vue 3 + Element Plus + ECharts | 综合大屏、金融分析、文本分析、电信分析、预警中心、数据查询 |
| **接口层** | FastAPI (Python) | 数据查询、AI预测、预警管理，统一提供 RESTful 接口 |
| **应用存储层** | MySQL | 存储聚合统计结果、AI分类结果、预警记录，支撑前端快速查询 |
| **计算层** | Java MapReduce + Scikit-learn | 结构化数据分布式聚合、投诉文本词频挖掘、AI文本分类 |
| **分布式存储层** | Hadoop HDFS | 存储原始清洗数据、MR 中间结果与输出结果 |
| **数据源层** | CFPB 金融投诉 + FCC 电信投诉 | 两套独立业务域数据，分开存储、分开计算 |

### 核心数据流

```
原始CSV → Python清洗 → HDFS存储 → MapReduce分布式计算 → 聚合结果入库MySQL → FastAPI接口 → Vue可视化展示
```

## 三、数据体系：三套数据、口径独立

### 核心原则：同业务分模块、跨业务不混算，所有指标口径可追溯

| 数据集 | 数据规模 | 核心字段 | 定位与用途 | 统计口径 |
| --- | --- | --- | --- | --- |
| **数据集B：complaints_clean.csv**   CFPB结构化全量 | 5.33GB | 日期、产品、州、企业、及时回复率等15个结构化字段，无投诉原文 | **金融投诉宏观大盘主数据源**   月度趋势、产品分布、州级分布、企业排行、回复时效等所有宏观指标 | 全量金融投诉，代表整体大盘 |
| **数据集A：17个CCDB_Export文件**   CFPB文本子集 | 约6GB | 比B多1列 `Consumer complaint narrative` 投诉原文 | **文本挖掘与AI分析专属数据源**   高频词统计、关键词提取、AI投诉分类训练 | 仅包含填写了自述文本的投诉，为文本子集，不用于总量统计 |
| **数据集C：fcc_consumer_complaints_clean.csv**   FCC电信投诉 | 586MB | 工单日期、投诉类型、州、通话方式等电信字段 | **独立业务域分析**   电信投诉月度趋势、类型分布、地区分布 | 电信业务独立统计，不和金融投诉合并 |

> 
> 答辩亮点：B 与 A 通过 `Complaint ID` 主键关联，AI 分类结果可回写到结构化投诉上；两套数据不强行合并，避免重复计数，保证指标严谨性。

## 四、核心功能与页面规划（6个核心页面）

### 页面1：综合数据驾驶舱（首页）

- **顶部指标卡**：金融总投诉量、电信总投诉量、带文本投诉量、整体及时回复率、覆盖州数量、涉及企业总数
- **核心图表**：双业务月度趋势对比折线图、金融产品占比、电信类型占比、企业TOP5、高频词预览
- **作用**：一屏总览两大业务领域全貌，是答辩演示的首屏核心。

### 页面2：金融投诉统计分析

- **筛选能力**：时间范围、产品类别筛选
- **核心图表**：
  1. 月度投诉趋势折线图
  2. 产品投诉TOP10柱状图 + 占比饼图
  3. 美国州级投诉热力图
  4. 涉事企业投诉TOP10排行榜
  5. 整体及时回复率指标卡 + 分产品回复率对比
- **数据来源**：全部来自 B 数据集的 MapReduce 计算结果。

### 页面3：金融文本与AI分析

- **核心模块**：
  1. 投诉高频词云 + TOP20柱状图
  2. AI 投诉分类交互：输入投诉原文，实时预测产品类别、输出置信度与关键词
  3. 模型评估指标展示：准确率、精确率、召回率、F1值
- **数据来源**：A 文本子集的词频统计 + Scikit-learn 训练的分类模型。
- **口径备注**：标注“仅基于填写了自述文本的投诉样本分析”。

### 页面4：电信投诉分析

- **核心图表**：月度趋势折线图、投诉类型TOP10柱状图、州级热力图、投诉渠道占比
- **数据来源**：C 数据集的 MapReduce 计算结果，独立业务域独立展示。

### 页面5：智能预警中心

- **核心逻辑**：基于月度投诉量，计算环比增长率，超过阈值自动生成预警（如环比>30%黄色预警，>50%红色预警）
- **页面元素**：预警总览卡片、带预警标记的月度趋势图、预警记录明细表（等级、原因、处置状态）

### 页面6：数据查询中心

- **筛选条件**：投诉编号、数据来源、日期范围、州、产品/类型
- **查询结果**：基础结构化信息；若为带文本的投诉，同步展示原文与AI分类标签。

## 八、答辩核心亮点与话术

### 1. 为什么三套数据分开计算，不合并？

> 
> CFPB 监管金融消费，FCC 监管电信通讯，业务场景和分类体系完全独立，总量相加没有业务含义；同属CFPB的两套数据，complaints_clean是全量结构化汇总，CCDB是带用户原文的子集，口径不同，合并会导致重复计数。我们采用「统一平台、两套业务、三个数据模块」的设计，保证所有指标口径严谨、结果可解释。

### 2. 怎么保证MapReduce计算的准确性？

> 
> 我们采用交叉验证方案：所有分布式计算结果，都和Python本地Pandas统计的结果做逐行比对，数值完全一致；同时统计结论符合人口分布、业务规律等常识，从两个维度保证了分布式计算的正确性。

### 3. 为什么原始数据存在HDFS，不直接存MySQL？

> 
> 原始数据规模超6GB，属于海量历史批处理数据，MySQL不适合存放大规模原始明细，查询性能也无法保障。我们的设计原则是：HDFS存原始数据做大数据计算，MySQL只存聚合后的结果，前端只查询汇总数据，兼顾了分布式存储能力和前端展示效率。
